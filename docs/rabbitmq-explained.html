The problem

Why put a queue between two services?

When a customer pays, Robot Shop must also ship the order. Shipping is slow and can fail. If payment called dispatch directly, the customer would wait for it, and a crashed dispatch would break checkout.

Direct HTTP call

payment → dispatch

  • Customer waits until dispatch finishes
  • Dispatch down = checkout fails
  • A burst of orders hits dispatch all at once
Through RabbitMQ

payment → broker → dispatch

  • Payment drops the order in a queue and replies at once
  • Dispatch down = orders wait in the queue
  • Dispatch works through the queue at its own pace

RabbitMQ is a message broker: a post office for services. The sender does not need to know who reads the message, where they run, or whether they are up right now.

Sequence

What happens during one checkout

  1. The browser calls POST /api/payment/pay/<user> with the cart. nginx in web forwards it to payment:8080.
  2. Payment checks the cart (it must include a shipping line), calls the payment gateway, and creates an order id (a UUID).
  3. Payment connects to rabbitmq:5672, declares the exchange robot-shop (safe to repeat), and publishes the order as JSON with routing key orders.
  4. The exchange checks its bindings. Key orders matches the binding to queue orders, so the message is stored there.
  5. Payment replies to the browser with {"orderid": "…"} straight away. It does not wait for dispatch.
  6. Dispatch is subscribed to orders. RabbitMQ pushes the message to it, and with auto-ack it is removed from the queue immediately.
  7. Dispatch logs Order {…} and "processes" the sale (in this demo, a short sleep).

Dispatch also declares the exchange, the queue and the binding when it starts. Whichever service starts first creates them; declaring something that already exists with the same settings does nothing. That is why the start order of the containers does not matter.

Source

The code, cut down to the RabbitMQ parts

payment/rabbitmq.py · producer 
# connect and make sure the exchange exists
conn = pika.BlockingConnection(params)   # host=rabbitmq, guest/guest
channel = conn.channel()
channel.exchange_declare(exchange='robot-shop',
                         exchange_type='direct', durable=True)

# publish one order
channel.basic_publish(exchange='robot-shop',
                      routing_key='orders',
                      properties=pika.BasicProperties(headers=headers),
                      body=json.dumps(order).encode())
dispatch/main.go · consumer 
// declare the same exchange, plus queue and binding
ch.ExchangeDeclare("robot-shop", "direct", true, false, false, false, nil)
q, _ := ch.QueueDeclare("orders", true, false, false, false, nil)
ch.QueueBind(q.Name, "orders", "robot-shop", false, nil)

// subscribe; 3rd argument true = auto-ack
msgs, _ := ch.Consume("orders", "", true, false, false, false, nil)
for d := range msgs {
    log.Printf("Order %s\n", d.Body)
}
Beyond this app

The four exchange types

Robot Shop uses direct. The type decides how the exchange matches a routing key to bindings.

TypeRoutes a message to…Typical use
directQueues whose binding key equals the routing key exactlyTask queues: orders, emails
fanoutEvery bound queue, ignoring the keyBroadcast: "order placed" to billing, stock and analytics
topicQueues whose pattern matches: * = one word, # = zero or moreorders.eu.*, logs.#
headersQueues whose header rules match the message headersRouting on several attributes at once

Lab: watch RabbitMQ on the running stack

Run these on the Ubuntu server, inside the robot-shop-docker folder, after podman-compose up -d --build. Use the latest code (git pull); older copies fail every checkout with "payment error". The outputs shown were captured from a real run.

Lab 4 Publish by hand, and see routing fail

command
podman-compose exec rabbitmq rabbitmqadmin publish exchange=robot-shop \
    routing_key=orders payload='{"orderid":"manual-001","user":"trainer","cart":{}}'

podman-compose exec rabbitmq rabbitmqadmin publish exchange=robot-shop \
    routing_key=wrong-key payload='{"orderid":"lost-001"}'
output
Message published
Message published but NOT routed

The first message shows up in the dispatch log. The second has no binding for wrong-key, so the exchange drops it silently: it never reaches any queue.

Reliability

What can go wrong in this setup

Robot Shop is a demo, and it takes shortcuts that a real shop should not. Each of these makes a good discussion point.

A durable queue is not the same as durable messages. The orders queue is durable, so it survives a broker restart. But payment publishes without delivery_mode=2 (persistent), so the messages inside it do not. We tested this: with dispatch stopped and 1 order waiting, podman-compose restart rabbitmq left the queue in place with 0 messages. The order was lost.
Auto-ack loses work if the consumer crashes. Dispatch consumes with auto-ack, so RabbitMQ deletes the message the moment it is delivered. If dispatch dies halfway through, that order is gone. With manual acks the consumer calls d.Ack() after finishing, and unacknowledged messages are re-delivered.
Unroutable messages vanish. As Lab 4 showed, a typo in the routing key drops the message without an error. The fix is to publish with the mandatory flag or to configure an alternate exchange.
Default credentials. Both services log in as guest / guest. That only works because they are on the same private container network. In production, create a dedicated user per service.
No volume for the broker. RabbitMQ's data lives inside the container. Removing the container (podman-compose down) deletes everything, even persistent messages, unless /var/lib/rabbitmq is on a volume.
Recap

Check yourself

Does payment send the order straight to the orders queue?

No. Producers always publish to an exchange (robot-shop). The binding with key orders is what puts it in the orders queue.

Dispatch is down for 10 minutes. What happens to checkouts?

They keep working. Orders pile up in the orders queue and dispatch processes the backlog when it comes back (Lab 3).

Why can the containers start in any order?

Both services declare the exchange (and dispatch also declares the queue and binding) when they connect. Declaring an existing object with the same settings is a no-op, and both services retry until the broker is reachable.

You want billing and analytics to get a copy of every order. What changes?

Bind two more queues (billing, analytics) to robot-shop with key orders, or switch to a fanout exchange. Payment does not change at all, which is the point of a broker.

Name two changes that would stop orders from being lost.

Publish persistent messages (delivery_mode=2) and use manual acks in dispatch. Also keep RabbitMQ's data on a volume.
